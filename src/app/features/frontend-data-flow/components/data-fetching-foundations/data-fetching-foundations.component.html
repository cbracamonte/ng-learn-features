01 · Fundamentos frontend

Una API es un contrato, no una función remota

El frontend profesional no acopla la UI directamente al JSON del backend. Traduce contratos, modela estados explícitos y protege a la persona usuaria de latencia, errores y respuestas inconsistentes.

Contrato HTTP

  • GET: lectura cacheable cuando el backend lo permite.
  • POST: creación o comando no necesariamente idempotente.
  • PUT/PATCH: reemplazo o actualización parcial con reglas claras.
  • DELETE: acción destructiva que necesita UX de confirmación y recuperación cuando aplica.

Estados de UI

  • Idle: todavía no hay intención o request.
  • Loading: la acción está en curso y debe ser visible.
  • Success: datos válidos para renderizar.
  • Empty: respuesta válida sin resultados.
  • Error: falla recuperable con mensaje accionable.

Errores reales

  • 400: input inválido; mapear a formulario o mensaje específico.
  • 401/403: sesión/autorización; no “ocultar” como error genérico.
  • 404: recurso inexistente o URL inválida.
  • 409: conflicto de concurrencia; requiere resolución, no retry ciego.
  • 5xx/network: retry condicionado, fallback u observabilidad.

DTO, dominio y ViewModel

DTO Forma externa del backend. Puede tener naming, fechas, nulls y campos técnicos que NO deben filtrarse sin pensar a la UI.

Modelo de dominio Reglas del negocio en el cliente: invariantes, permisos visuales, estados permitidos y transformaciones confiables.

ViewModel Lo que el componente necesita para pintar: texto, flags, acciones habilitadas y mensajes listos para UX.

Nota Expert: si tu componente conoce demasiado del DTO, tu UI queda secuestrada por el backend. La frontera sana suele vivir en services/facades/mappers, no repartida en cada template.
