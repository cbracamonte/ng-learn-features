03 · Estado remoto, caché y concurrencia

El problema difícil no es pedir datos; es mantenerlos correctos

Cuando el usuario escribe, navega, reintenta o dispara acciones rápidas, el frontend debe decidir qué request sigue siendo válido, qué dato se muestra y cuándo se invalida.

Cancelar

Para búsqueda o filtros vivos, el request anterior puede quedar obsoleto. En RxJS, este caso suele modelarse con switchMap si la fuente soporta cancelación.

Encolar

Para guardados secuenciales donde el orden importa, conviene serializar. No todo click repetido debe paralelizarse.

Ignorar

Para submit en curso, puede ser correcto ignorar acciones repetidas hasta terminar, además de deshabilitar controles por UX.

Resolver conflicto

Si dos clientes editan el mismo recurso, un 409 no se arregla con retry ciego. Necesitas política de merge, refresh o decisión del usuario.

Caché: las preguntas correctas

  • ¿La respuesta depende del usuario, permisos, idioma o feature flags?
  • ¿Cuándo se invalida: tiempo, mutación, navegación, evento externo?
  • ¿Se permite stale-while-revalidate o debe bloquear hasta refrescar?
  • ¿Dónde vive la caché: interceptor, service, store, browser/CDN o servidor?

Optimistic UI con responsabilidad

  • Aplica cuando la operación es predecible y reversible.
  • Guarda snapshot para rollback si falla.
  • Muestra estado pendiente para evitar mentirle al usuario.
  • No ocultes conflictos de autorización, validación o versión.
Nota Expert: RxJS y signals no compiten aquí; resuelven capas distintas. RxJS modela tiempo, cancelación y streams; signals modelan estado actual y derivaciones para UI. Un diseño Senior sabe dónde termina uno y dónde empieza el otro.
