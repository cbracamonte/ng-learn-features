Testing: demostrar notificaciones reales

Un test zoneless valioso no fuerza el DOM para ocultar un problema: prueba que el componente notifica a Angular de la misma forma en que lo hará en producción.

Evita como diseño nuevo

  • fakeAsync(), tick() y flushMicrotasks() son utilidades basadas en Zone.js.
  • fixture.detectChanges() tras cada mutación puede hacer pasar un componente incompatible.
  • Modificar propiedades comunes del componente sin una notificación de render.

Prefiere en zoneless

  • Interactuar como usuario o actualizar signals expuestas por la UI.
  • Esperar la sincronización programada con await fixture.whenStable().
  • Proveer zoneless en TestBed si la suite aún carga Zone.js.
TestBed.configureTestingModule({
  providers: [provideZonelessChangeDetection()]
});

const fixture = TestBed.createComponent(CounterComponent);
fixture.componentInstance.count.set(1); // signal consumida en template
await fixture.whenStable();             // Angular realiza el render notificado

expect(fixture.nativeElement.textContent).toContain('1');

Lectura precisa de detectChanges()

No es una API prohibida: suites existentes pueden seguir utilizándola. El riesgo es usarla para esconder que producción nunca calendarizaría ese cambio. Para código nuevo, deja que Angular renderice después de una notificación real y espera estabilidad.

Regla expert · El test debe fallar por la razón correcta

Si una propiedad mutada silenciosamente aparece en pantalla solo porque el test invocó detectChanges(), probaste una ficción. En zoneless, el contrato bajo prueba incluye la notificación que habilita el render.
