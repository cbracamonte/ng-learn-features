Notas senior RxJS (visual + avanzado)

✅ Estrategias de flattening: lectura senior

  • switchMap: cambia de contexto. Cancela el inner anterior porque el último intent vale más que el previo.
  • concatMap: preserva orden y no pierde eventos. Tradeoff: aumenta latencia si la cola crece.
  • mergeMap: maximiza rendimiento(throughput) con trabajo paralelo. Tradeoff: podés perder orden y saturar backend.
  • exhaustMap: protege una sección crítica mientras hay un inner activo. Ideal submit/login/pagos.

🧪 Definiciones detalladas de pipe operators

  • map: proyección pura. Cambia forma del dato, no el tiempo ni la cantidad de emisiones.
  • filter: guard clause reactiva. Reduce ruido antes de entrar a operadores caros.
  • debounceTime: compacta bursts temporales; excelente para inputs humanos, mala idea para eventos que no deben perderse.
  • distinctUntilChanged: compara contra la emisión inmediatamente anterior. Con objetos, sin comparator custom, compara referencia.
  • tap: observabilidad y side effects no críticos. Si tu lógica depende de tap, probablemente está mal ubicada.
  • startWith: define estado inicial del stream para UI o composición temprana.
  • catchError: intercepta error en el tramo actual. OJO: dónde lo pongas cambia qué parte del pipeline se recupera.
  • finalize: cleanup transversal; corre en complete, error o unsubscribe.

🔗 Composición y caching

  • forkJoin: sincronización final. Útil cuando TODAS las fuentes deben completar para renderizar algo coherente.
  • combineLatest: cálculo reactivo continuo. Pensalo como una planilla que recalcula con el último valor de cada columna.
  • withLatestFrom: evento principal + contexto. El stream secundario no “dispara”; solo aporta snapshot.
  • zip: lockstep estricto. Une emisión 1 con 1, 2 con 2; útil cuando necesitás pairing determinista.
  • shareReplay: multicast + replay. Comparte una ejecución y entrega el último valor a suscriptores tardíos.
  • shareReplay con refCount: libera source cuando no quedan suscriptores. Sin estrategia, podés dejar procesos vivos o cache eterna.

⚠️ Anti patrones RxJS

  • Nested subscribes: fragmenta flujo, errores y cleanup. Componé con operadores, no con callbacks encadenados.
  • Exponer Subjects públicamente: rompe encapsulación. Exponé asObservable(), no el write API.
  • shareReplay(1) por reflejo: sin pensar lifecycle/cache invalidation es una bomba de memoria o datos stale.
  • mergeMap para acciones no idempotentes: podés disparar writes simultáneos y dejar estado inconsistente.
  • distinctUntilChanged con objetos mutables: si mutás la misma referencia, el operador no te salva conceptualmente.
  • tap para lógica de negocio: convierte el pipeline en una casa con cables por afuera. Difícil de testear y razonar.
  • catchError al final sin criterio: puede “comerse” errores importantes y dejar la UI silenciosamente rota.
  • No modelar loading/error/empty: stream bonito, UX mala. La reactividad no reemplaza el diseño de estados.

🧠 Reglas senior para decidir

  • Primero definí la semántica de concurrencia: cancelar, encolar, paralelizar o ignorar. Recién ahí elegís el operador.
  • Distinguí cold vs hot observables: si cada suscripción repite trabajo, evaluá multicasting/caching conscientemente.
  • Diseñá streams como contratos de dominio, no solo como trucos de UI.
  • Si una decisión afecta orden, idempotencia, cache o lifetime, ya es una decisión arquitectónica, no “solo RxJS”.
