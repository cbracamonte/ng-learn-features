Notas senior: microfrontends sin humo

🧠 Definiciones claras

  • Microfrontend: partición de frontend por dominios/equipos con despliegue y evolución parcialmente independientes.
  • Federation: cargar código remoto en runtime sin rebuild completo del host.
  • Remote: aplicación o módulo expuesto para ser consumido por otro.
  • Host/Shell: aplicación contenedora que orquesta navegación, layout y composición.

📌 Qué mirar antes de elegir

  • Autonomía real de equipos: si no existe, quizá no necesitás microfrontends.
  • Versionado compartido: Angular, design system, auth SDK, router contracts.
  • Observabilidad: logs, métricas y trazas cross-app.
  • Fallback UX: qué pasa si un remote no carga.

⚠️ Anti patrones

  • Romper un monolito frontend en 8 remotes cuando tenés un solo equipo.
  • Compartir estado global de forma caótica entre remotes.
  • Acoplar remotes por imports internos no versionados.
  • Creer que microfrontends arreglan mala arquitectura de dominio. NO la arreglan.

✅ Regla práctica

Elegí Native Federation si querés alinearte con Angular moderno y minimizar dependencia futura de webpack. Elegí Webpack Module Federation si tu organización ya invirtió ahí y el retorno de migrar es bajo.

🔥 La verdad incómoda

El problema difícil NO es cargar un remote. El problema difícil es gobernanza: contratos, ownership, compatibilidad, CI/CD, observabilidad, rollback y disciplina de equipos. Si eso no existe, la federación es maquillaje.

Verificado con fuentes primarias: Webpack Module Federation es una feature oficial de webpack 5; Native Federation se presenta como enfoque browser-native/ESM y en Angular moderno suele usarse con tooling de Angular Architects.
