Parte 1 · Base conceptual

Signals: un grafo explícito de estado y consumidores

Pregunta frecuente Senior

Un signal es un contenedor de valor que notifica a quienes lo consumen cuando cambia. La lectura con () importa: durante un contexto reactivo Angular registra qué consumidor depende de qué productor. No es simplemente “una variable que actualiza HTML”.

Productor

signal()

Posee estado mutable: usuario, filtro, selección o contador.

Derivación

computed()

Lee productores y calcula un valor sin duplicar estado.

Consumidor

Template / effect

Lee señales; Angular registra la dependencia que debe reaccionar.

Modelo mental para explicarlo en entrevista

  1. 1. Creo estado con signal().
  2. 2. Leo signals dentro de template o derivaciones.
  3. 3. Angular forma dependencias precisas.
  4. 4. Al cambiar el productor, invalida consumidores pertinentes.

Lo que aporta al diseño

  • Lectura síncrona del valor actual: user().
  • Actualizaciones explícitas con set() y update().
  • Derivaciones declarativas, lazy y memoizadas mediante computed().
  • Granularidad adecuada para estado de UI y compatibilidad natural con zoneless.

Lo que NO reemplaza automáticamente

  • Operadores temporales, cancelación o combinación compleja de eventos: RxJS sigue siendo relevante.
  • Inmutabilidad profunda: asReadonly() no impide mutar objetos internos.
  • Modelado responsable: múltiples signals mal elegidas también crean estado inconsistente.

Regla Senior · Define ownership antes de elegir API

Primero responde: “¿quién es dueño de este estado y qué consumidores necesitan reaccionar?”. Un signal es excelente para estado síncrono de UI. Un stream puede ser el owner correcto para eventos o pipelines asíncronos complejos. Convertir en el borde es arquitectura; convertir por reflejo es deuda.
