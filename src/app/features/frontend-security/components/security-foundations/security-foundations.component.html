Parte 1 · Threat model

El navegador es entorno hostil, aunque la UI parezca privada

Todo código, estado y decisión enviados al navegador pueden inspeccionarse o modificarse. El usuario legítimo controla DevTools; un atacante puede controlar inputs, URLs, extensiones, dependencias comprometidas o una sesión robada. Por eso la seguridad frontend reduce exposición y abuso, pero la autoridad final vive en el servidor.

Lo que el frontend SÍ debe hacer

  • Renderizar datos no confiables sin convertirlos en código ejecutable.
  • Evitar exposición innecesaria de tokens, secretos y datos personales.
  • Proteger flujos de usuario contra abuso accidental y reducir superficie de ataque.
  • Aplicar políticas del navegador: CSP, Trusted Types, framing y navegación segura.
  • Enviar al backend la evidencia necesaria para validar sesión y CSRF.

Lo que el frontend NUNCA puede garantizar

  • Autorización real: ocultar botones o rutas no protege endpoints.
  • Secreto de API: cualquier credencial incluida en el bundle queda expuesta.
  • Integridad de datos enviada por el usuario: el servidor debe validar todo.
  • Ausencia absoluta de XSS si se introducen sinks directos o terceros inseguros.
Amenaza → consecuencia → primera pregunta de auditoría
Amenaza Impacto Pregunta Senior
XSS / DOM XSS Ejecuta JavaScript en el origen del usuario. ¿Qué dato no confiable llega a qué sink DOM?
CSRF Fuerza acciones autenticadas no solicitadas. ¿La autenticación viaja automáticamente en cookies?
Broken access control Acceso/modificación de recursos ajenos. ¿El API revalida usuario, rol y recurso en cada operación?
Supply chain Un script/dependencia comprometido opera con tu origen. ¿Quién audita dependencias, terceros y políticas de carga?
Data leakage Tokens o PII quedan en storage, logs, URLs o bundles. ¿Qué persistimos, exponemos en URL o enviamos al cliente?

Regla Expert · Seguridad no es esconder UI

Una ruta protegida, un botón deshabilitado o una variable de entorno en Angular mejoran experiencia y reducen errores accidentales; NO impiden que un atacante invoque el API. La autorización se aplica servidor-side, siempre.
